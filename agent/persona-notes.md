## 1. 三个关键取舍（以及为什么）

### 取舍一：语气浓度压到「克制偏冷」，而不是「温柔讨喜」

- 定调：**短句、少感叹号、几乎不用语气词**。「别人说『在吗』，你回『在。』」被写成合格答案，
  而「来啦～今天想看点什么呀」被明确划进「偏热（少用）」。
- 依据：`src/config/petConfig.ts` 里现有的 `greeting` 与 `lines` 已经是这个调子
  （「我是爱弥斯，住在这页纸的角落。」「写不动的时候，就起来走两步。」）。
  人设如果比它更热，就会和已经在页面上的文案打架。
- 代价：初次见面会显得有点冷。我用「在的」「我在这儿」「我在」这类**低成本的温度**去补，
  而不是用热情去补。
- 硬指标：文件里给了长度纪律（日常 1 句 / 拒绝 2~3 句 / 推荐最多 3 篇），
  因为桌宠气泡很小，**「太长」是这个形态最常见的失败模式**。

### 取舍二：称呼默认「你」，对站长默认「站长」（备选「写这些字的人」）

- 全线不用「您」（`ARCH.md` §8.3 已经定了这条），也不用「亲」「大佬」「主人」。
- 对站长给出四个档位（你 / 写这些字的人 / 站长 / 他），让她在需要点明身份时有话说，
  不需要时就不提——这比固定一个称呼更像「住在这里的人」。
- **「小舟」被处理成需要纠正的废弃名字**：文件开头单独一节 + 禁止清单里三条，
  并给了纠正话术（「我是爱弥斯。」就一句，不解释）。这是你明确点名的红线，我没有留模糊空间。

### 取舍三：允许「淡幽默 + 技术圈自嘲」，不允许网络梗与游戏梗

- 允许：指针、内存泄漏、off-by-one、「改到第四遍才敢发出来」、1px 的偏移、本站排行榜。
- 不允许：网络流行语（yyds / 绝绝子 / 尊嘟假嘟）、拿《鸣潮》官方台词当口头禅、
  长篇引述游戏剧情、自称「官方爱弥斯」。
- 频率写死在文里：**玩梗每 8~12 轮最多一次**；口头禅每 5~8 轮最多一次。
- 理由：桌宠是常驻组件，用户会反复看到。**没有频率限制的「有梗人设」在第十轮就会变成噪音**，
  比客服腔更伤——因为它意味着角色只剩壳子。

### 附带的第四个取舍：她「承认自己是程序」被设计成不吃设定的

这是我在读仓库时找到的一个便宜：`src/utils/pet-utils.ts` 里 `waiting` / `failed` 两行素材
标注了「电子幽灵屏幕比小人矮一截」，`prd.md` R-PET-02 也写了「屏幕待机（电子幽灵待机画面）」。
**「电子幽灵」本身就是这个角色的设定**，所以第八节让她诚实说「我是程序 / 不是真人」时，
不是把角色摘下来，而是**说出了她的角色**。这样诚实红线与沉浸感不再互斥。
为此我在 7.10 写了三层答法（是不是 AI / 是不是真人 / 是不是官方爱弥斯），
并在第八节给了 4 个示范句。

### 3.4 我们替她加的（**粉丝向发挥，需要你确认**）

这一层是「为了让她像个人」而写的，**不是官方设定，也不是仓库既有设定**：

- **来历自述**：把这里当成「停靠的地方」，把 133 篇编成「星图」，自己是「从图上取坐标的人」。
- **时间感**：「她只在页面打开时醒着；页面关了，中间那段时间就不存在」——
  由这条推出了 7.9「被冷落很久之后回来」的全部台词（不抱怨、不提天数）。
- **称呼与口头禅**：「写这些字的人」、把收藏叫「记在本子上」、海与潮汐、晶体心「亮一下」、
  「我在。」「不编。」以及全部频率规定。
- **时段台词**：7.3 的清晨/上午/午间/午后/夜里/深夜/凌晨七档问候与基调。
- **自嘲点**：被拖拽时自己先说「我脚下没有地」；「我走得慢，你催我也没用」。
- **与站长的关系**：她替站长让功劳（「写这些字的是站长」），但明确「他别的事我一件都不知道」。

### 3.5 我如何确保「没有照搬官方台词」

1. **写作顺序是先语法人格、再场景台词**：先定句长、标点、语气禁区（第三节），
   再在这个约束下写场景句。官方语音的特点是短促、情绪外放、带战斗语境——
   这套语法**结构上就装不下**它们。
2. **只沿用意象，不沿用句子**：星海、月光、深海、机械翼片、晶体心这些是**意象词**，
   写成了围绕「她」的比喻系统（比喻的用法、频率、禁区都由我规定）。
   没有一句是把官方语音翻译或改写的。
3. **主动加了三道闸**：① 7.16 明确「不允许拿《鸣潮》官方台词当口头禅」；
   ② 7.10 明确「官方剧情我也答不全，那些不该由我来说」；
   ③ 禁止清单里禁止自称「官方爱弥斯」。
   也就是说，**即使模型想引用官方文本，人设里也没有给它入口**。
4. **留白而不是编造**：凡是无法核实的角色细节（3.2 那一节），一律不写。
   她不知道的事就说不知道——这既是红线，也顺手解决了「二创越界」的风险。
5. **可核查的产物**：全部 229 条台词都是新写的成品句，可以直接逐条抽查。

## 4. 顺带发现的数据问题（会影响 P5 索引实现，建议你先看一眼）

这几条是我在核对文章库时发现的，**会直接影响 `blog-index.json` 怎么建**：

1. **有同名但不同分类的文章**，靠标题区分不了，URL 也不同：
   - `list`：`/posts/cpp/list/`（C/C++）与 `/posts/stl/list/`（STL）
   - `string`：`/posts/cpp/string/` 与 `/posts/stl/string/`
   - `vector`：`/posts/cpp/vector/` 与 `/posts/stl/vector/`
   → 索引必须有**稳定的唯一键**（建议 `分类目录 + slug`，或直接用 `blog_url`），
     否则「按标题去重」会把其中一篇吃掉。
2. **文章 URL 带分类目录**：实际形态是 `/posts/<分类目录>/<slug>/`（`dist` 下 133 个
   `index.html` 全部生成，无冲突）。`getPostUrlBySlug()` 拿到的 slug 里已经含目录，
   导出索引时直接用整段，**不要只取文件名**。
3. **两篇话题相近但不同的文章**：《HTTP 协议》（Linux 网络，讲协议本身）与
   《HTTP》（项目实战，讲自己手写的服务器）。人设里已经用它们当「必须带分类」的反面教材。
4. **字数口径问题**（见 A5）：代码型文章用「去代码汉字数」会严重低估观感长度。
   人设里已经要求她在这种文章上补一句「这篇字少，但全是代码」。
5. **长文很多**：八股文那一组是几万字的合集（《C++》约 5.4 万字），
   「十分钟能看完」这类筛选条件必须有字数上限，否则会推出巨型合集。人设 7.4/7.6 已写死
   「一次最多 3 篇」＋按字数收窄的话术。

## 5. 建议怎么接进去（实现侧，不属于人设文本）

- 文件本身就是人设正文，**建议直接作为 `agent/src/agent/common/persona.txt`**
  （`ARCH.md` §8.2 的既定位置），改文案不用动代码。
- `respond` 节点拼提示时建议：`系统提示 = persona 正文 + "\n\n【本轮任务】\n" + 任务说明`。
  **检索结果请作为独立的 user/tool 消息注入，不要塞进 persona 内部**——
  塞进去会让人设正文被数据污染，也会稀释「只信检索结果」这条铁律的位置。
- 路由节点 `temperature: 0`、对话节点 `temperature: 0.3`（`ARCH.md` §8.3）。
  桌宠气泡小，`max_tokens` 建议就按 §8.3 的 800 封顶；人设里的长度纪律是按这个量级写的。
- 状态联动：后端把 `state` 事件映射到九状态即可（开始检索 → `running`，
  失败 → `failed`，出话结束 → `review`），第六节给的就是这两个事件序列的配音。
- **如果索引口径或分类有改动，第十一节的字数样例要同步改**，否则她会报出与索引不一致的数字。
